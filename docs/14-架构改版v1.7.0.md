# v1.7.0 架构改版：Avalonia 取代 WPF，换机器能直接跑

> 起因：用户反馈「这个项目和上一个项目（hgvd-downloader）一样，换机器后无法运行」。
> 结论：发行方式与源码里的本机硬编码路径是病根，跟界面框架无关 —— 但界面框架顺手换掉，
> 因为 WPF 做不出自包含单文件、也只能跑 Windows。

## 一、诊断出的四个根因

| # | 根因 | 证据 |
|---|---|---|
| 1 | 发行包是 **framework-dependent 目录 zip** + `gui/启动.bat` | 新机器没装 .NET 8 桌面运行时，双击就报错退出 |
| 2 | 源码里**硬编码作者本机路径** | `D:\Program Files\Netease\MuMu`、`ffmpeg-8.0.1...\bin`、`adb.exe`、固定设备 `192.168.1.101:5555`、`C:\Users\<user>\Downloads` |
| 3 | WPF 天生绑 Windows，且**不能自包含单文件** | 运行时依赖系统，换机器即碎 |
| 4 | Python 版 v1.6.1 已从仓库删除，**改一行逻辑必须先过 C# 编译** | 迭代成本高，试想法不划算 |

```
  src/Xqd.Avalonia

```

WPF 的两个工程（`Xqd.Gui`、`Xqd.Controls`）已删除；历史保留在 git 与
远程分支 `csharp-wpf`。

## 三、去本机化：唯一入口 `Setup/ToolLocator.cs`

所有「外部程序在哪」的问题都收敛到这一个类，别处不许再写死路径。

| 工具 | 查找顺序 |
|---|---|
| ffmpeg / ffprobe | `~/.xqd_tool/ffmpeg/bin`（自装目录）→ `tools.json` 点选记录 → `XQD_FFMPEG_DIR` → PATH |
| MuMuManager | `tools.json` 点选记录 → `XQD_MUMU_MANAGER` → `XQD_MUMU_HOME` → Program Files / Program Files (x86) / ProgramW6432 / LOCALAPPDATA 常见目录 → **各固定盘 `Netease\MuMu*`** → 限深 2 搜索 → PATH |
| adb | 点选记录 → `XQD_ADB` → MuMu 同级 `adb.exe` → PATH |
| 设备 | `XQD_ADB_DEVICE` → 否则 `adb devices` 取第一台在线设备 |

★ 实测教训：MuMu 12 的默认安装目录是 **`Netease\MuMuPlayer-12.0`**，
早期候选列表只有 `Netease\MuMu`，于是「机器上明明装了」也被判成未安装
（本机就是这种：`D:\Program Files\Netease\MuMuPlayer-12.0`）。现已补全带版本号后缀的目录名。

下载目录不再写 `C:\Users\<用户名>\Downloads`，改为读注册表
`User Shell Folders` 的「下载」Known Folder（本机已被用户重定向到 `D:\download`），
读不到才回落 `%USERPROFILE%\Downloads`。

## 四、界面（Avalonia）

功能与 WPF 版对齐：

- **单表 8 列**：状态胶囊 / 课程（自适应宽度）/ 所属营 / 时长 / 大小 / 速度 / 剩余 / 进度；
- **无边框窗口** + 自绘最小化/最大化/关闭 + 8 个缩放热区 + 顶栏可拖；
- 左侧营列表（分组小标题、同名营加序号、三态全选），勾选即把课表并入右侧同一张表；
- 5 个视图切换（全部/待下载/下载中/已完成/失败）+ 画质下拉 + 重新扫描 / 重置记录；
- 暂停 / 继续 / 取消 / 开始下载；最多 3 路并发；右键：下载 / 重试 / 复制课名 / 打开文件夹 / 删成品；
- 历史（含残件清理）、汇总条、日志区、状态栏版本号；Ctrl+Q 退出；
- 关于窗（版本/运行时/配置目录/下载目录/快捷键）、环境检查窗（依赖状态 + 一键装 ffmpeg + 指定 MuMuManager）。

Viewport 细节：Avalonia 的 `TopLevel.PointToScreen` 是 `IRenderRoot` 的
**显式接口实现**，直接调用会编译报「名称不存在」，必须
`((IRenderRoot)this).PointToScreen(p)`。

# v1.7.1：换机器拿不到授权（对齐 hgvd-downloader 的修复）

> 反馈：新机器上 MuMu 开着、App 也登录了，点「重新授权」始终失败 —— 与
> hgvd-downloader 修复前的现象完全一致。

## 三个根因（hgvd 那边已经踩过）

| # | 根因 | 现象 |
|---|---|---|
| 1 | **只按固定目录找 MuMuManager** | 用户把 MuMu 装在自己建的目录（或 `Netease\MuMuPlayer-12.0` 之外的布局）→ 直接报「找不到 MuMuManager.exe」 |
| 2 | **实例号写死 `-v 0`** | 多开时用户只开了实例 2/3，`sh -v 0` 读不到 Cookie → 误判「App 未登录」 |
| 3 | **没装 App 的实例被当成「没登录」** | 机器换了、App 还没装，提示永远是「App 未登录」，用户以为要重新登录 |

## 修法

**① 定位升级为七级探测**（`Setup/ToolLocator.FindMumuManager`）：

```
点选记录 → 环境变量 → 运行中的 MuMu 进程 → 开始菜单/桌面 .lnk
        → 卸载注册表(DisplayName 含 MuMu) → 各盘目录枚举(名字含 MuMu/Nemu) → PATH
```

- 进程这条最可靠：授权时模拟器必然开着，`MainModule.FileName` 就是真路径，装哪都拿得到；
- 快捷方式用 `WScript.Shell` 解析 `TargetPath`（安装包必建 `.lnk`）；
- 注册表读 `InstallLocation` / `DisplayIcon`（去掉 `,0`）/ `UninstallString`；
- 每个候选都做「**向上回溯 3 层 + 拼相对位置**」，兼容
  `nx_main\`（MuMu 6/12）、`shell\`、`nx_device\shell\`、根目录直放。

**② 实例 0~7 全探**（`MumuAuth.ListInstancesAsync` + `ChooseInstanceAsync`）：

- `info -v i` 逐台问，谁在跑就记谁；
- 多开时**逐台试读 Cookie**，先看这台上有没有装兴趣岛 App，再挑第一台真有
  `userId` + `rsessionId` 的；
- 多台都有登录态时**联网验证**（`QianliaoPlatform.CheckAuthAsync`），取服务端认可的那台；
- 全都验证不了（断网）就退回第一台并提示，不把用户挡在门外。

**③ 兜底交互**：

- 点「重新授权」时若连 MuMuManager 都定位不到，**直接弹文件选择框**让用户选一次
  （记住到 `tools.json`，下次不再问）；
- 授权流程内部报「找不到 MuMuManager.exe」时也会自动弹一次并重试；
- 选中的实例里没装 App → 明确提示「请在实例 N 里安装并登录兴趣岛」，而不是含糊的「App 未登录」。

**④ 排障入口**：`xqd-downloader --authcheck` 打印

```
MuMuManager：<实际路径>
实例数：2
  实例 0  运行中  MuMu安卓设备  ✓ 有登录态
  实例 1  运行中  MuMu安卓设备-1  ✗ 没有 userId/rsessionId
→ 会使用实例 0
```

只报「有没有登录态」，不输出任何 cookie 值。

## 回归

新增 L 组 **11 项**（用临时目录模拟任意安装根，不依赖本机是否装了 MuMu）：

- `nx_main` / `shell` / `nx_device\shell` / 根目录直放 / 向上回溯 3 层；
- 不存在的路径不抛异常；
- `DisplayIcon` 去 `,0`、带引号命令行去引号；
- 真实 `.lnk` 解析出 `TargetPath`；
- `FindMumuManager` 不抛异常。

总计 **292 项通过 / 0 失败**。本机 `--authcheck` 实测正确识别实例 0 有登录态、
实例 1 没有，并选中实例 0。

## ⑤ 边等边取：引导式等待窗（对齐 hgvd 的 §4.4）

前四条解决「找得到、挑得对」，但换机器最常见的场景是：**实例开着、App 没装/没登录，
用户得先动手**。此时直接报错只会让人反复点「重新授权」。

`MumuAuth.WaitForLoginAsync(timeoutSec, onStatus, ct)` + `Views/WaitAuthWindow`：

- 置顶小窗，标题「等待模拟器登录」，一行状态 + 日志框 + 倒计时 + 取消；
- 每 **2 秒**扫一遍实例 0~7：没运行实例就提示「请先打开 MuMu 模拟器」；有运行实例就
  逐台「装没装 App → 能不能读到 header」；
- 任一实例读到登录态 → 立刻关窗，把实例号交回主界面，自动 `RunAuthOnceAsync(force)`
  重读一次授权，无需用户再点；
- 默认最多等 **180 秒**（可 `--waitauth 30` 调整），超时给「已超时，请确认…」文案；
- 同一句错误只播报一次，不刷屏。

主界面接线（`MainWindow.EnsureAuthAsync`）：MuMu 兜底选择之后，若仍然失败且原因是
「App 未登录 / 未检测到登录态 / 没有「兴趣岛」App」（`NeedsWaitForLogin`），就弹等待窗；
返回实例号 ≥ 0 才重跑授权，点取消（-1）则停在原提示，不打扰。

**独立入口**：`xqd-downloader --waitauth [秒数]` 只开等待窗、不加载主界面，关掉即退出。
远程指导用户排障时可以直接让他跑这一条，看到窗→登录→窗自动消失，就说明链路通了。
本机实测：实例 0 已登录，启动后 **约 10 秒**（8 台实例轮询 + 一次 header 读取）自动关窗、
进程退出码 0。

## ⑥ 顺手修掉 build.cmd 的 LF 陷阱

`build.cmd` 之前以 **LF 换行 + 中文注释** 保存，cmd.exe 会把它按行错切，表现为：

```
'设置' is not recognized as an internal or external command
'.csproj"' is not recognized as an internal or external command
```

即脚本「跑一半就散架」，用户照 README 执行必然失败。现改为 **纯 ASCII + CRLF**，
并要求保持该格式（脚本首行注释已写明）。修后本机 `build.cmd` 一把过，产物
`dist\xqd-downloader-v1.7.1.exe`（44.0MB，`--version` = 1.7.1）。
