# 兴趣岛视频下载器（GUI）

单文件桌面工具，把课程批量导出为通用 MP4。当前只支持兴趣岛，
但平台层留好了扩展接口。

## 怎么用

**方式一：直接双击**（推荐给日常使用）

```
D:\user\chisenin\Desktop\xingqudao-downloader-v1.5.3.exe
```

单文件，约 97 MB，绿色免安装。
★ **v1.5.1 起平时启动不启动 MuMu**：直接使用本机保存的授权；
只有首次使用、或点「重新授权」时才会拉起模拟器（见下方「授权」）。
（v1.4.0 及更早版本没有「多营勾选 / 标题前缀 / 封装流水线」。）

**方式二：源码运行**（方便改）

```bash
python xqd_gui.py
```

需要 `PySide6`（`pip install PySide6-Essentials`）。

### 操作流程

1. **授权**：顶栏显示「授权：已就绪（本机保存）」。
   ★ **平时启动直接用已保存的授权，不启动 MuMu**，也不必等模拟器开关机。
   只有两种情况才拉起模拟器：① 本机还没保存过授权（首次使用）；
   ② 授权过期、营列表加载不出来时点顶栏「重新授权」刷新。
   真正走模拟器时，顶栏两个勾选框控制「自动启动 / 授权后自动关闭」。
2. **选营**：左栏选「正式营 / 体验营」。**点营名前的方框可勾选多个营**
   （标题栏「全选」一次全勾），勾中的营课程会合并进同一张课程列表；
   一个都不勾时仍显示当前高亮的那个营。多营名在标题里用「·」分隔并向左循环滚动
3. **选课**：右栏勾选课程，或双击某行直接下载该课。
   第一列「标题前缀」是该课在**原营**里的序号（多营合并不重排），
   「进度」列会显示真实进度（重新载入课表也不归零）
4. **下载**：点「下载选中」，每节课下方有进度条。
   一节进入「封装中」后网络即被释放，队列里的下一节会立刻开跑
5. **暂停**：随时点「暂停」停住全部下载，点「继续」接着下
6. **失败重试**：失败的课会自动重新勾选，再点「下载选中」即可重下
7. **管理**：下方「下载管理」可「清除列表」（只清列表）或「删除文件」（移到 `_已删除`）

### 下载管理表的「剩余时间」

「下载管理」表实时显示每个任务的**实测速度**和**预计剩余时间**，
估算会随网络快慢和剩余内容多少**实时变化**（不是固定值）。

| 列 | 内容 |
|---|---|
| 状态 | 解析中 / 下载中 / 封装中 / 校验中 / 已完成 / 失败（**进行中的阶段之间可自由切换**） |
| 大小 | 下载中显示「已下/总量」（如 `42.0/145 MB`），完成后显示成品大小 |
| 速度 | **实测字节速率**（`5.0MB/s`），超过 6 秒没有新进度就显示 `--` |
| 剩余时间 | 倒计时（`00:31`），完成后变成「用时 01:24」 |

标题旁还有**全局汇总**：`剩余约 12:30 · 3 个在跑 / 20 个排队`。

> ★ **「速度」列是字节速率，可以直接和系统工具对照**
> （Windows 任务管理器的「网络」/「磁盘」、`iperf3` 等）。
> 早期版本这里显示的是「内容倍速」（如 `248`），被误按字节渲染成
> `248B/s`，与任务管理器的 84 Mb/s 完全对不上 —— 已修。

#### 两种速率，两种用途（不要混用）

工具内部同时维护**两个独立的速率计**：

| 速率计 | 喂进去的量 | 单位 | 用途 |
|---|---|---|---|
| `job['bmeter']` | 已下载**字节数** | B/s、KB/s、MB/s | 「速度」列显示、**直链音频**的 ETA |
| `job['meter']` | 已下载**内容时长**（秒） | 内容秒/秒（倍速） | **分片视频**的 ETA 计算 |

- 两者**互不干扰**，各自独立的滑动窗口。
- 直链音频（MP3/M4A/AAC）没有分片时长可用 → 退回字节口径，
  此时 `job['unit'] == 'byte'`。
- 分片视频 → `job['unit'] == 'dur'`，ETA 用内容速率。

**时间显示格式**：`天:时:分:秒`，按需省略前导的零单位 ——
只有秒时不显示「分:」，只到分时不显示「时:」，只到时不显示「天」：

| 实际时长 | 显示 |
|---|---|
| 45 秒 | `45` |
| 90 秒 | `1:30` |
| 1 小时 1 分 1 秒 | `1:01:01` |
| 1 天 2 时 3 分 4 秒 | `1:02:03:04` |

最高位段不补零，其余各段一律两位。

估算规则：

- **下载阶段**：`剩余时长 ÷ 最近几秒的实时速率`。
  用的是**最近 8 秒**的滑动窗口，不是全程平均 ——
  网络一慢下来估算立刻跟着变，不会「卡在某个值不动」。
- **进度用时长占比，不用字节占比**：清单里每片的时长是精确已知的，
  而总字节数是**抽样外推**的估算值，按字节算百分比会偏。
- ★ **总字节数靠「均匀抽 12 片」外推**（不是取前 3 片）。
  实测一节 2485 片的直播课：前 3 片外推偏高 **37.3%**（1574 MB vs 真实
  1146.5 MB）；改成跨全清单等距抽 12 片后误差 **-0.7%**。
  原因：直播课录制**开头几分钟码率高于全片均值**，用开头几片代表全片必然高估。
  抽样片会**写盘复用**，不额外浪费请求。
- **封装阶段**（转封装 MP4）：按「片子总大小 ÷ Z 盘写入速度 +
  时长 ÷ 60」估算，另有约 3 秒给 ffprobe 校验。
- **暂停时冻结**：暂停期间倒计时不跳变，看着像任务丢了。
- 速率暂时测不出来时（刚开始那几秒），显示 `--`；
  任务结束后最后一列显示实际「用时」。

#### 状态列的阶段流转

状态列由 `job['phase']` 驱动，可在**所有进行中阶段之间自由切换**：

```
解析中 → 下载中 → 封装中 → 校验中 → 已完成
```

> ★ 曾经的坑：守卫白名单只写了 `('下载中', '排队中')`，
> 于是状态一旦变成「解析中」就**再也变不回「下载中」** ——
> 界面上一直卡在「解析中」，实际早就在下载。
> 现在白名单是模块级常量 `PHASE_TEXTS`，包含全部进行中阶段，
> 同时**保护终态**（已完成 / 失败）不被阶段刷新覆盖。

### 顶栏两个开关

| 勾选框 | 默认 | 作用 |
|---|---|---|
| 自动启动 MuMu | 开 | MuMu / 安卓设备没运行时自动拉起（拿授权需要） |
| 授权后自动关闭 | 开 | 拿到授权后自动关掉兴趣岛 App 与安卓设备 |

「自动关闭」有个重要语义：**只关本工具自己启动的东西**。
若模拟器是你手动开的，工具不会替你关，只在提示条里说明。

会话状态记在 `xqd_auth._SESSION` 里 —— 这样即使用户在「App 未登录 →
去登录 → 点重试」的场景下，第二次运行时依然认得出「这是工具启动的」，
照样会关掉。

### 课程表第 0 列的复选框

这一列表示**这节课在不在当前下载流程里**：

| 复选框 | 含义 |
|---|---|
| 勾上 | 该课已入队 / 正在下载 / 刚下完（点「下载选中」时会带上它） |
| 空的 | 该课不需要下载（已存在完整成品，或还没选） |

要点：

- **入队即自动勾上**。不管是勾选后点「下载选中」，还是双击某行
  「下载此课」，那一行都会立刻显示对勾 —— 否则看上去像「启动了下载
  但勾选却是空的」，与实际状态不符。
- 扫描到**完整成品**的行会取消勾选（它不用再下了）；
  扫描到**残缺文件**的行会勾上（需要重下）。
- 迟到的扫描结果**不会**把「排队中 / 正在下载」的行取消勾选 ——
  那种情况下下载状态比扫描结论更权威。
- 反过来，**已完成 / 失败**的行允许被扫描结果覆写：上一轮下完的课，
  这一轮扫描发现文件确实存在，就该标成「已存在」并取消勾选。
  （`camp_catalog` 缓存了 Lesson 对象，状态会跨「重新加载课表」残留，
  所以这里必须让扫描结论能覆盖。）

### 暂停 / 继续

课程表工具栏上，「下载选中」右边是**「暂停」**按钮（橙色）。

- **暂停**：所有正在进行的下载**立刻停住**，不再发出新的网络请求；
  队列里排着的课也不会启动
- **继续**：从暂停的地方**接着下** —— 已下好的分片保留在临时目录里，
  不会重头再来
- 按钮文案在「暂停」/「继续」之间切换；没有任务在跑时按钮是灰的
- 运行中的行会显示 `[已暂停]`，日志里也会记一行

实现要点（`xqd_engine.DownloadControl`）：

| 方法 | 作用 |
|---|---|
| `pause()` / `resume()` / `toggle()` | 切换暂停状态 |
| `stop()` | 要求中止（关窗口时用，解除暂停避免线程卡死） |
| `wait_resume()` | 暂停时阻塞等待；已中止则返回 False |

暂停是**协作式**的：各下载线程在**领下一个分片之前**检查标志并等待，
所以暂停期间不会有半截请求卡在中间。

断点续下的关键：`download_segments` 会跳过 `dest_dir` 里**已存在且非空**
的分片文件，所以「暂停 → 继续」不会重复下载。

直链音频（AUDIO 类）走 `download_direct`，改成 **64KB 一块流式读取**，
这样进度能实时上报，中途也能暂停（之前是整文件读完才报一次进度）。

实测（`_lel/api/test_pause_real.py`，真实网络）：
暂停时 2972 个分片 → 2 秒后仍是 2972 个（零新增请求）→ 继续后
成品 414.3s，与课表 414.0s 吻合。

### 已下载检测（自动跳过 / 覆盖重下）

下载前会检查该节课**是否已有成品**，判定维度是「文件名主键 + 时长」
（不查哈希、不联网查大小 —— 见 `xqd_dedupe` 模块头的成本表）。

判定是**整组**的：主名 `序号.课名.日期` 加上历史遗留的 `-1`/`-2`
重名后缀，都算同一节课。

| 情况 | 处理 |
|---|---|
| 组里有**完整**文件 | **跳过**，只在日志里记一行，**不弹窗** |
| 组里只有**残缺**文件（过小/无法解析/时长不符） | 删掉残件，用规范名**覆盖重下** |
| 一个文件都没有 | 正常下载 |

残缺文件判定后会被自动清理，所以不会再出现
`xxx.mp4` 与 `xxx-1.mp4` 这种同一节课两个文件的混乱。

文件名规范也改了：**不再产生 `-1`/`-2` 后缀**。
序号参与主键，营内本就唯一，加后缀只会制造重复。

### 课程列表的列结构与表头计数

**v1.5.0 起共 6 列**（列号集中在 `xqd_gui.COL_*` 常量，界面与测试都引用它）：

```
[✓]  标题前缀  课程                       标题后缀    时长    进度
      01       第一讲  [已完成]            2026.04.18  45:00   ▓▓▓▓░
      02       第二讲  [下载中]            2026.04.19  45:00   ▓▓░░░
```

* **标题前缀**（第 1 数据列）：该课在**原营**课表里的序号（`01`、`02`…）。
  ★ 多个营合并时**不按合并行号重编号** —— 甲营 01/02/03、乙营 01/02/03，
  与成品文件名 `<序号>.<课名>.<日期>.mp4` 完全对应。
* **课程**（第 2 数据列）：纯课名 + **紧跟课名的状态词**（方括号 `[已完成]`）。
  状态词**各状态独立配色**、课名保持深色（`LessonTitleDelegate` 自绘，
  不是整格染色）。**表头带括号计数** `课程 (12/61)` —— 已下载 / 全部。
* **标题后缀**（第 3 数据列）：**成品文件名里标题后面那段日期**
  （`YYYY.MM.DD`），与落盘文件名同源。例：`1.【复训营课程1】养正十三式复习.2026.04.18.mp4`
  → 显示 `2026.04.18`。
* **进度**（最后 1 列）：**重新载入课表也显示真实进度，不留空条** ——
  活动任务用实时进度；已完成的课 100%；未完成的按下载历史
  （`done_dur/total_dur` 或 `down/total`）与可续传的分片缓存取最大值；
  目录里已有成品但历史没记上（手工拷入）也判 100%。
  扫描判定「已存在」置 100%，判定「需重下」则回退到缓存的真实部分进度。
* 上课时刻（`MM.DD HH:MM`）、营名、成品文件主名都在 **tooltip** 里。

★ **变更沿革**：v1.3.0 把状态词搬进「标题后缀」列 → v1.4.0 按用户要求
改回跟在课名后面、「标题后缀」改显示文件名日期 → v1.5.0 把序号从课名里
**单列成「标题前缀」第一列**，课名列只放纯课名。

★ 表头计数在扫描过程中**实时更新**（不必等整个目录扫完）。
★ 多营合并时，标题里的营名用「·」分隔并**向左无缝循环滚动**
（`MarqueeLabel`，短文本/单营不启动定时器），鼠标悬停看完整名单。

### 三处状态一一对应

同一节课的状态会显示在**三个地方**，它们用的是**同一套词**：

| 位置 | 例子 |
|---|---|
| ① 课程列表**课名后面**的方括号 | `晚间课堂：五种意志力+阶段性回顾 [封装中]` |
| ② 下载管理表「状态」列 | `封装中` |
| ③ 运行日志 | `[14:07:22] 封装中：晚间课堂：五种意志力+阶段性回顾` |

**状态词全集**（两处状态列完全一致）：

```
已存在   排队中   解析中   下载中   封装中   校验中
已完成   失败     已暂停   需重下
```

各阶段含义：

| 词 | 含义 |
|---|---|
| `已存在` | 下载目录里已有完整成品（检测出来的） |
| `排队中` | 已入队，等前面的课下完 |
| `解析中` | 正在解析 HLS 清单 |
| `下载中` | 正在下载分片 |
| `封装中` | 分片下完，正在转封装成 MP4 |
| `校验中` | 正在用 ffprobe 校验时长 |
| `已完成` | 本次下载完成 |
| `失败` | 下载出错 |
| `已暂停` | 已被用户暂停 |
| `需重下` | 已有文件残缺，将重新下载 |

★ 课程列表的状态词会**跟着阶段实时变**（解析中 → 下载中 → 封装中 → 校验中），
不是一直停在「下载中」。

★ **暂停/恢复**两处也同步：暂停时都显示「已暂停」，
点继续后回到各任务**真实的阶段**（可能正处在封装，不会笼统写「下载中」）。

★ **终态不会被覆盖**：任务已完成/失败之后，迟到的阶段信号改不回中间态。

★ 阶段日志用 `log_state()` 写，**不抢底部状态栏** ——
否则每节课 4 行阶段日志会让底部的字不停闪，把「完成/失败」冲掉。

### 封装阶段流水线（v1.5.0）

用户 2026-11-07 指出：**一节即将下完、进入「封装」时，网络流量已经被解放了**，
此时应当能开始一个新的下载进程。

引擎的阶段是 `解析 → 下载 → 封装 → 校验`；从 `封装` 起，
拼接分片（`cat` 字节拼接）、ffmpeg 转封装、ffprobe 校验**全部只读本地磁盘**，
不再发一个 HTTP 请求。旧逻辑却让这个线程一直占着 3 路并发槽位之一，
队列里的下一节只能干等，带宽白白空着。

v1.5.0 把并发上限拆成两种资源：

| 资源 | 上限 | 谁占用 |
|---|---|---|
| **网络槽位** | `MAX_LESSON_WORKERS = 3` | 处于 `解析` / `下载` 的任务 |
| **本地封装槽位** | `MAX_MUX_WORKERS = 2` | 处于 `封装` / `校验` 的任务 |

- 阶段一变成「封装中」，`_on_phase` 立即把网络槽位还回去并 `_pump_queue()`，
  **队列里的下一节马上开跑** —— 稳态是「3 节在下载 + 最多 2 节在封装」。
- 限住封装路数是因为成品写在 Z 盘（SMB，实测约 10 MB/s），
  多个大文件同时拼接会互抢 IO，反而拖慢所有任务。
  没抢到封装槽位的任务暂时继续占着网络槽位，等有封装任务结束后再释放。
- 「下载管理」标题旁显示 `N 个在跑（X 下载 / Y 封装）/ Z 个排队`，
  一眼能看出流水线在跑，而不是误以为并发上限被突破。
- 暂停时仍然**不启动新任务**（槽位记账照常），点「继续」会把缺的槽位补上。

实现细节与几个易写反的条件见 `docs/11` L 节。

### 下载历史：关掉工具再打开，列表和进度都还在

「下载管理」表的内容与进度会被**持久化**：

* 记录文件：`%USERPROFILE%\.xqd_tool\history.json`
* 分片缓存：`%USERPROFILE%\.xqd_tool\parts\<key>\`

| 场景 | 表现 |
|---|---|
| 关掉工具再打开 | 「下载管理」表恢复上次的记录（课名 / 状态 / 已下大小） |
| 上次失败或没下完 | 标成 **「未完成（可续传）」** |
| 恢复的行 | **默认不勾选** —— 不会自动重下，要续传自己勾一下 |
| 重新勾选那一课 | **接着上次的位置继续下**，已下的分片不重下 |
| 点「清除列表」 | 清掉任务表**和历史记录**，不动已下载的文件 |
| 点「删除文件」 | 移走成品，历史记录一并清除 |

**为什么进度能跨会话恢复**（已实测）：

HLS 分片的**文件名在两次会话之间完全稳定**（实测 150/150 一致，
连顺序都一样），只有 URL 上的签名 `?sign=` 会变。
所以按文件名落盘就能复用已下分片。

★ 实测端到端（`_lel/api/test_history_real.py`，真网络）：
第一次故意断网 → 缓存保留 257 个分片 → 第二次会话**只请求 43 个分片**
（257 个一个字节没重下）→ 成品 47.9MB / 599.1s（标称 599s）。

★ 引擎里 `download_lesson` 的 `seg_dir` 参数就是这个缓存目录。
**失败/中止时必须保留**它（成功才清）—— 弄反了续传就废了。

★ 分片缓存的清理策略：启动时清掉「已完成」记录对应的残留目录；
**「失败」和「未完成」的保留** —— 那是续传的本钱。

### 授权与 MuMu 的「no Qt platform plugin」弹窗（v1.5.1 已根治）

**症状**：从打包的 exe 启动工具、自动授权时，连着弹出几个标题为
`MuMuManager` 的英文错误框：

> This application failed to start because no Qt platform plugin could be
> initialized. Reinstalling the application may fix this problem.
> Available platform plugins are: windows.

重装 MuMu 没用 —— 本机 `Qt5Core.dll` / `Qt5Gui.dll` /
`plugins/platforms/qwindows.dll` 齐全且同版本构建，系统 / 用户级
也**没有**任何 `QT_*` 环境变量。

**根因**：本工具是 PySide6（**Qt6**）程序。PyInstaller 的
`hooks/rthooks/pyi_rth_pyside6.py` 在打包程序运行后**无条件**写入：

```
QT_PLUGIN_PATH   = <_MEIPASS>\PySide6\plugins    ← Qt6 插件目录
QML2_IMPORT_PATH = <_MEIPASS>\PySide6\qml
PATH             = <_MEIPASS>;<原 PATH>
```

子进程默认继承。MuMu 全家是 **Qt5** 程序，某些子命令
（`control launch` 会连带拉起主程序）一旦初始化 `QGuiApplication`，
就会去 `QT_PLUGIN_PATH` 找平台插件，加载到 **Qt6 的 `qwindows.dll`**，
符号对不上 → 弹框。授权流程一次要调十几次 `MuMuManager`，故连弹好几个。
源码方式运行（`python xqd_gui.py`）不注入这些变量，因此只在打包 exe 上
复现 —— 这就是「反复出现、时有时无」的原因。

**两层修复（v1.5.1）**：

1. **环境隔离（`xqd_proc.py`）**：所有子进程创建时净化 `QT_*` / `QML*` /
   `_PYI_*` / `_MEIPASS2`；命令若指向 `MuMuManager.exe`，再显式把
   `QT_PLUGIN_PATH` / `QT_QPA_PLATFORM_PLUGIN_PATH` 指向 **MuMu 自带的
   Qt5 插件目录**、从 PATH 剔除 `_MEI*` 临时目录与 `PySide6` 目录、
   cwd 设为 MuMu 安装目录。`control launch` 拉起的主程序是**孙进程**，
   继承这份净化后的环境，整条链路都被纠正。
2. **干脆不调用（`xqd_gui.py` + `xqd_creds.py`）**：启动时优先读
   `%USERPROFILE%\.xqd_tool\cookie.txt`（或环境变量 `XQD_COOKIE`），
   有就用，**一个 MuMuManager 都不调**；只有首次使用或点「重新授权」
   才走模拟器，拿到新 Cookie 后写回私有文件供下次复用。
   弹窗连触发机会都没有，还省掉每次 13 秒启动 + 28 秒关闭模拟器。

★ 凭据文件在仓库之外，绝不硬编码；离线回归设了 `XQD_TEST_HOME` 时
`save_cookie()` 会拒绝写真实凭据（读取不受影响，真网络测试照常用）。

★ 若**手动**双击 MuMu 也弹同样的框，那是另一回事（MuMu 自身安装损坏），
本机静态检查已排除。旧版 exe（v1.5.0 及更早）没有这两层修复，
仍可能弹框 —— 请改用 v1.5.3（或更新版本）。

## 文件命名


## 授权：免 adbd 通道 ★

**这是本工具最关键的设计。** 兴趣岛 App 是 WebView 壳，登录态存在：

```
/data/data/com.qlchat.xingqudao/app_webview/Default/Cookies
```

这张 SQLite 表的 `encrypted_value` 列**是空的**，`value` 直接明文存储
`userId` / `rsessionId`。

怎么在**不经过 adbd** 的前提下读到它？用网易 MuMu 自带的 `MuMuManager.exe`：

```bash
MuMuManager sh -v 0 -c "sqlite3 '/data/data/com.qlchat.xingqudao/app_webview/Default/Cookies' \
  \"select host_key,name,value from cookies where host_key like '%qianliao%';\""
```

`sh` 子命令走的是**模拟器内部 RPC**，不是 adb 协议（adb 是独立通道），
而且在 root 上下文执行：

```
uid=0(root) gid=0(root) groups=0(root) context=u:r:nemuinit:s0
```

所以整条链路 **MuMuManager CLI → 内部 RPC → root shell → sqlite3**，
全程不启 adb、不用 adb 连接、不依赖 adb 端口。

### 踩过的坑

| 坑 | 现象 | 正解 |
|---|---|---|
| **参数顺序** | `MuMuManager -v 0 info` 打印帮助并返回非 0 | **子命令在前**：`MuMuManager info -v 0` |
| 应用未安装 | `pm list packages` 空 | 先 `control app launch --package <pkg>` |
| 未登录 | Cookie 表里没有 `userId`/`rsessionId` | 拉起 App 让用户登录，再点「重试」 |
| Cookie 域名 | 同名 cookie 有多个 host | 取**顶层域**（`.qianliao.net`）优先，它对所有子域生效 |

### 扩展到新平台

实现一个 `Platform` 子类并注册即可，**GUI 侧不用改任何代码**：

```python
class MyPlatform(Platform):

    display_name = '我的平台'
    camp_kinds = ('正式营',)

    def list_camps(self, kind):  ...   # -> [Camp]

REGISTRY[MyPlatform.platform_id] = MyPlatform
```

顶栏的平台下拉框会自动出现新平台。

## 技术选型说明

**PySide6（Qt）** 而不是 Electron / Tkinter：

- 纯 Python 栈，与已有下载内核同语言，没有跨语言边界
- QSS 样式表能做出现代扁平风格（见 `QSS` 常量）
- 可用 PyInstaller 打成单个 exe
- 系统里原本**连 tkinter 都没有**，PySide6 是唯一能做出漂亮界面的选择

## 已知约束

- **ffmpeg 必须可用**：优先找 PATH，其次找
  `D:\user\chisenin\download\Programs\ffmpeg-8.0.1-essentials_build\bin`，
  再找 `C:\LEL\LEL-Downloader\Source\ffmpeg`
- **必须禁用系统代理**：业务网关与 CDN 请求都要 `ProxyHandler({})`，
  否则被代理吞掉返回 HTML
- **成功码在 `state.code`**（不是顶层 `code`）
- **转封装用 cat 字节拼接**，不要用 ffmpeg concat demuxer ——
  后者会重置时间戳，实测成品比清单长 6 秒（230.8s vs 224.6s）
- **分片临时目录逐个删**：批量删除会触发安全删除钩子的阈值（50）被拦，
  临时目录会一直累积
