## A. 免 adbd 拿授权（MuMu 内部 RPC）

```
MuMuManager sh -v 0 -c "sqlite3 '/data/data/com.qlchat.xingqudao/app_webview/Default/Cookies' \
  \"select host_key,name,value from cookies where host_key like '%qianliao%';\""
```

| # | 坑 | 说明 |
|---|---|---|
| A1 | `sh` 不是 adb 协议 | 走**模拟器内部 RPC**，且 `uid=0(root)`，所以不需要 adbd 授权 |
| A2 | 参数顺序 | **子命令在前、`-v` 在后**：`MuMuManager info -v 0` 正常；`MuMuManager -v 0 info` 打印帮助返非 0 |
| A3 | Cookie 表结构 | App 的 WebView 表 `encrypted_value` **为空**，`value` 明文存 userId / rsessionId |
| A4 | SQL 通配符 | `like '%%x%%'` 是**字面匹配两个百分号**，匹配不到任何行 → 必须写 `'%x%'`（旧代码写 `%%` 却以为会被格式化，表现为误判「App 未登录」） |
| A5 | 同名 cookie | 取**顶层域**（`.qianliao.net`）优先 |
| A6 | 域名覆盖 | 必须含三个：`.qianliao.net` / `.xqdaolove.cn` / **`.nicegoods.cn`**（rsessionId 也可能写在 nicegoods 域） |
| A7 | 设备已关 | `sh` 返回 `{"errcode":-201,"errmsg":"vm not running"}` —— 这段 JSON **不是空输出**，不识别会误判「App 未登录」。用 `xqd_auth.vm_not_running()` |

### MuMu 自动启停

| 层 | 命令 | 判定 |
|---|---|---|
| 主程序（多开器 UI） | `MuMuManager main launch` / `main close` | tasklist 查 `MuMuNxMain.exe` |
| 安卓设备实例 | `MuMuManager control -v 0 launch` / `shutdown` | `info -v 0` 的 `is_android_started` |

- `main` / `control` **没有** `-v`（`main` 是全局的）。
- ★ **直接 `control launch`**，主程序会被连带带起来（13 秒就绪）。
  反过来先 `main launch` 再 `control launch` **会卡住**（多开器起来后接管了设备启动请求）。
- `control shutdown` 是**异步**的 → 轮询 `info` 等 `is_android_started` 变 False（约 28 秒）。
- 会话状态记在 `xqd_auth._SESSION`（main/device）→
  「App 未登录 → 登录 → 点重试」第二次运行时依然认得出「这是工具启动的」，照样会关掉。

## B. 速率 / ETA 计算（GUI v6.1 修复）

- **两种速率必须用两个独立速率计**：
  - `job['bmeter']` 喂**字节** → `job['speed']` → 「速度」列（可与任务管理器对照）
  - `job['meter']` 喂**内容时长** → `job['rate_dur']` → 分片视频的 ETA
  - 混用一个 → 248 倍速被 `fmt_speed()` 按字节渲染成 `248B/s`。
  - `job['unit']`：`'dur'`（分片视频）/ `'byte'`（直链音频，无分片时长）。
  - `_compute_eta` / `_job_eta` / `_tick_eta` / `_update_global_eta` 全按 unit 分流。
- **总字节必须均匀抽样外推，不能取前 3 片**：`xqd_engine._sample_segments()`，`_SAMPLE_COUNT=12` 等距取样。
  实测 2485 片直播课：取前 3 片外推 **+37.3%** → 均匀 12 片 **-0.7%**
  （直播课**开头码率高于全片均值**）。抽样片写盘复用，不浪费请求。
- 进度用**时长占比**（每片时长精确，总字节数是外推估算）。
- 封装阶段按 Z 盘写速单独估算；暂停时冻结倒计时。

## C. 三处状态一一对应（GUI v8）

- 状态词表**单一事实来源**：模块级 `PHASE_TEXT` / `STATE_TEXTS` / `STATE_COLORS`。
- `_set_both_states(job_id, word, msg=None, force=False)` 同步更新
  「课程列表后缀」+「下载管理状态列」。
- **终态守卫**：`if not force and job.get('finished') and cur.text() not in PHASE_TEXTS: return`
  —— 迟到的阶段信号会把「已完成」改回「下载中」。
  ★ `force=True` 用于**写入终态本身**，少了它终态写不进去。
- `log()` 会抢底部状态栏 → 阶段日志另开 `log_state()`（只写日志框和文件，不动状态栏）。
- **状态列守卫白名单必须含全部进行中阶段**：
  `PHASE_TEXTS = ('下载中','排队中','解析中','封装中','校验中')`
  —— 只写前两个 → 变成「解析中」后再也变不回「下载中」。
- `STATE_COLORS` 存的是字符串，`setForeground` 需要 `QColor` → 写入时转换。

## D. 下载历史 + 跨会话续传

- HLS **分片文件名跨会话 150/150 一致**（顺序也一致），只有 `?sign=` 变 → 按文件名落盘即可复用。
- 引擎签名：`download_lesson(..., seg_dir=None, keep_parts=False)`。
  ★★ 清理条件必须是 `if own_dir or (ok_result and not keep_parts)` ——
  写反成 `not ok_result` 会**把续传本钱删掉**（失败时反而删分片）。
- 分片缓存目录：`%USERPROFILE%\.xqd_tool\parts\<md5(abspath(out_path))[:16]>\`
- 历史文件：`%USERPROFILE%\.xqd_tool\history.json`（上限 500 条）。
- `merge` 按**成品路径**主键；**已完成 / 失败不被「排队中 / 下载中」覆盖**；进度只前进不后退。
- 恢复的行**默认不勾选**（不自动重下）；用户重新勾选才续传。
- 启动时清理「已完成」的残留分片；**「失败」「未完成」必须保留**（那是续传的本钱）。
- 实测：第一次断网留 257 片 → 第二次**只请求 43 片**（257 片一个字节没重下）
  → 成品 47.9MB / **599.1s**（标称 599s）。

## G. 文件操作与测试隔离

- **SMB 网络盘上不要逐个 `os.path.exists`** 几百个候选文件名（会慢到 8 分钟跑不完）
  → 一次 `listdir` 再在内存里匹配。
- 直链音频（AUDIO 类是 MP3）的临时文件**必须用 `tempfile.mkstemp`**，
  放营目录共享名会被并发下载互相覆盖 → 产出截断成品。
- **批量删除文件会触发安全删除钩子阈值（50）** → 分片清理改用**截断**
  （`open(p,'wb')`），同样释放磁盘空间但不触发钩子。
- 删除带盘符前缀的路径会被安全钩子拦（`SAFE_DELETE_INVALID_PATH`）→ **用相对路径**
  （先 `cd` 到目标目录再 `rm -rf ./xxx`）。
- **测试必须设 `XQD_TEST_HOME`** 隔离配置 / 历史 / 分片缓存，否则跑一次测试就把用户
  真实 `~/.xqd_tool` 改成临时目录（`Z:\太极营` 差点丢）。
- **真网络测试的采样点必须放 `on_phase` / `on_progress` 回调里** ——
  `download_lesson` 同步阻塞主线程，`QTimer` 根本没机会触发（等于没测）。

## K. 凭据脱敏的坑（2026-11-07 实战）

- ⚠️ **半遮半掩最危险**：此前把 rsessionId 前半段换成 `<REDACTED>`、
  却把**尾巴留在下一行**（Python 隐式字符串拼接），等于没脱敏。
  扫描时要同时看**整行**和**跨行拼接**两种形态。
- ★ 正则按**整行**匹配会漏掉「尾巴单独成行」的情况 ——
  必须另加一条「单独成行的尾巴」规则。
- ★ `git filter-branch --tree-filter` 里：
  - 脚本**不能**放在仓库里（tree-filter 的检出目录是 `.git-rewrite/t`）；
    放外部绝对路径 + `os.getcwd()`。
  - `GIT_WORK_TREE='.'` 时 `abspath` 会解析到 `.git-rewrite` 父目录 ——
    **别用它**，用 `os.getcwd()`。
  - 脚本里打印的「改动 N 个文件」计数在 filter-branch 环境下**不可靠**
    （明明改了却显示 0）；以 `git grep` 扫历史为准。
- ★ 重写历史后**必须**再做：
  ```
  git reflog expire --expire=now --all
  rm -rf .git/refs/original
  git gc --prune=now --aggressive
  ```
  否则悬空 commit / blob 里仍留着含凭据的旧版本
  （`git cat-file --batch-all-objects` 能扫出来）。
- 验证要用 `git grep` 遍历**所有 ref 的所有提交**，而不是只 grep 工作区。

## L. v1.5.0：多营合并 / 标题前缀 / 进度恢复 / 封装流水线

### 列号必须走常量

课程表从 5 列变 6 列（勾选框 / **标题前缀** / 课程 / 标题后缀 / 时长 / 进度），
`COL_CHECK … COL_PROGRESS`、`LESSON_COLUMN_COUNT` 是**唯一事实来源**。
踩过的坑：状态词委托、进度条、表头计数、`_set_row_state`、
`_mark_existing`、暂停同步、以及 4 个回归测试文件里都写死过 `1`/`2`/`4`，
加一列后**整体错位**（测试表现为「课名列是空的、状态词读不到」）。
现在界面与测试一律 `xqd_gui.COL_*`。

### 多营合并的三条硬约束

1. **序号不重排**：`_append_lesson_rows` 用 `i + 1`（营内下标），
   不是合并后的行号。甲营 01/02/03、乙营 01/02/03 是**期望行为**，
   因为成品文件名前缀就是营内序号。
2. **每行绑自己的营**：`camp_of_row[row]` 决定输出目录、已下载检测、
   历史主键。`_scan_existing` 参数改成 `[(camp, lessons), ...]` 按营分组扫描，
   不能共用一个 folder；旧两参数调用仍兼容。
3. **键里带营**：`row_of_lesson` 的键用 `_lesson_key(le, camp)`（含营名），
   直接拿 `le.key = (camp, index)` 会在假数据 / `camp=''` 时跨营互相覆盖。

### 后台线程别被 GC

多营课表用 `CatalogWorker` 后台拉，`_catalog_gen` 作废旧结果；
**运行中的 QThread 必须存进 `_catalog_workers` 保活**，
否则引用一丢被 Python 析构，Qt 会 `qFatal` 直接 abort（无 traceback）。
扫描线程同理（`_scan_workers`）。

### 进度列恢复的优先级

`_initial_progress(le, camp)`：活动任务（`jobs` 里 `lesson is le`）
→ 下载历史（已完成 100%；否则 `done_dur/total_dur`、`down/total`
与分片缓存字节数取最大，**上限 99%**，未完成不许满格）
→ 磁盘上已有成品但历史没记上（100%）→ 0。
`_mark_existing(row, ok=False)` 要把之前乐观置满的 100% 拉回真实部分进度。

### 封装流水线（最容易写反的三处）

- 占网络槽位的是**还没下完分片**的任务，不是「线程还活着」的任务。
  `running_workers` 保留全部在跑任务，新增 `network_released` 记已归还槽位的，
  `_net_active() = running_workers - network_released`。
  `_pump_queue` 的判据必须是 `_net_active() < MAX_LESSON_WORKERS`，
  再加一个 `len(running_workers) < MAX_LESSON_WORKERS + MAX_MUX_WORKERS` 硬上限。
- **释放时机只有三处**：`_on_phase` 进入 `封装/校验`、
  `_on_download_completed` 完成、`toggle_pause` 继续。
  完成回调里必须 `network_released.discard(job_id)` 并再跑一次
  `_release_idle_slots()` —— 否则「封装槽位空出来了但那个还占着网络槽位的
  任务没被释放」，队列会莫名卡住。
- **暂停判断要放在槽位记账之后**：`_on_phase` 里先释放再判 `_paused`，
  `_pump_queue` 内部自己检查 `control.is_paused()` 并 `break`。
  反过来写会让暂停期间槽位账不准，继续后并发数对不上。

平均带宽估算（`_update_global_eta`）要**排除** `network_released` 的任务，
否则封装中的任务仍带着下分片时的 `rate_dur`，会把排队任务折算得偏快。

## M. v1.5.1：MuMu「no Qt platform plugin」弹窗（★ 反复出现，已根治）

### 症状与排除过程

打包 exe 自动授权时连弹几个标题为 `MuMuManager` 的错误框：
`This application failed to start because no Qt platform plugin could be
initialized. Available platform plugins are: windows.`

先排除「MuMu 装坏了」：`D:\Program Files\Netease\MuMu\nx_main\` 里
`Qt5Core.dll` / `Qt5Gui.dll` / `Qt5Widgets.dll` /
`plugins/platforms/qwindows.dll` 齐全、同为 2026-10-23 构建；
`qwindows.dll` 的导入依赖（`freetype.dll` / `MSVCP140.dll` /
`VCRUNTIME140*.dll`）都在同目录；`qt.conf` 只有 `[Paths]`（无重定向）。
系统 / 用户级环境变量也**没有** `QT_*`。→ 不是安装损坏，不是系统级污染。

### 真正的根因

`PyInstaller/hooks/rthooks/pyi_rth_pyside6.py` 在**打包程序运行后**
无条件执行：

```python
os.environ['QT_PLUGIN_PATH']   = <_MEIPASS>/PySide6/plugins    # Qt6
os.environ['QML2_IMPORT_PATH'] = <_MEIPASS>/PySide6/qml
prepend_path_to_environment_variable(sys._MEIPASS, 'PATH')
```

子进程默认继承 → MuMu 的 Qt5 程序初始化 `QGuiApplication` 时加载
**Qt6 的 `qwindows.dll`** → 符号不匹配 → 弹框。
授权链路每次启动要调十几次 `MuMuManager`（`is_running` / `ensure_device` /
`sh` / `close_all`…），所以连弹好几个。
源码运行不注入这些变量 → 只在打包 exe 上复现，
这就是「不止一次、时有时无」的原因。

★ 探测时注意：`info -v 0` / `help` / 无参数都**不初始化 Qt GUI**，
在污染环境下照样正常返回，别拿它们判断「有没有污染」。真正会炸的是
`control launch` 连带拉起主程序那条 GUI 路径（含**孙进程**）。

### 两条最容易写错的地方

1. **净化要做在子进程创建处，不是改自己进程的环境**。
   改自己的 `QT_PLUGIN_PATH` 会弄坏本工具的 Qt6 界面；
   而且 MuMu 主程序是孙进程，只改 MuMuManager 的环境也来不及。
   `xqd_proc.run/popen/check_output` 统一在每次创建时构造 env，
   **一处覆盖全链路**。
2. **不能全局剔 PATH 里的 `_MEIPASS`**：打包版 ffmpeg 可能要那里的 DLL。
   只有识别出命令是 `MuMuManager.exe` 时才剔 `_MEI*` / `PySide6` 目录。

### 第二层：让弹窗没有机会出现

GUI 启动时先 `xqd_creds.load_cookie()`；有就直接就绪、加载营列表，
**一个 MuMuManager 都不调**。只有「无缓存」或用户点「重新授权」
（`auto_check_auth(force_mumu=True)`）才走模拟器；拿到新 Cookie 用
`xqd_creds.save_cookie()` 落盘，下次继续零 MuMu 调用。

★ 三个易错点：
- 按钮必须强制 `force_mumu=True`，否则 Cookie 过期时点它仍读缓存，永远刷不掉。
- `save_cookie()` 在 `XQD_TEST_HOME` 存在时**拒绝写真实凭据**（读取不受影响），
  否则离线回归会覆盖用户真实 Cookie。测试要验证写入需显式传 `path`。
- `test_autolaunch.py` 是专门验证「自动启停 MuMu」的真机用例，
  必须改成 `auto_check_auth(force_mumu=True)`，否则新默认行为让它永远跑不到。

### 验证

`_lel/api/test_mumu_env.py` **52 项全绿**（净化 / MuMu 专用 env /
非 MuMu 保留 PATH / 显式 env 尊重 / 凭据隔离 / 缓存优先 / 强制刷新 /
无缓存回退 / 加载失败提示）。离线回归合计 **403 项全绿**。
净化后真实调用 `MuMuManager info -v 0` 仍返回正常 JSON（rc=0）。

## N. `csharp-wpf` v1.5.2：全选 ↔ 勾选框联动（2026-11-08）

> **历史记录**：这一节描述的是当时独立 `csharp-wpf` 分支上的修复；
> v1.5.3 起两套实现已合并到 `master`，修复代码现在位于 `src/Xqd.Gui/`。
> 合并与 CI 发版见根目录 `README.md` / `.github/workflows/release.yml`。

### 现象（用户截图）

营列表里表头「全选」已打勾、左下计数显示「9 个营 · 已勾选 9 个」，
但下面 9 个营的方框**全是空的**；单独勾/取消某个营时表头三态也不跟手。

### 根因（★ 只影响 C# / WPF 版，Python 版无此问题）

`Xqd.Gui/ViewModels/NotifyBase.cs`：

```csharp
protected void Raise([CallerMemberName] string name = null) => ...
```

`CampItem.SetCheckedSilently()` / `LessonRow.SetCheckedSilently()` 里写的是**无参**
`Raise()`。编译器填的 `CallerMemberName` 是**调用它的方法名**
`SetCheckedSilently`，不是属性名 `IsChecked`。

而 DataTemplate 里是 `IsChecked="{Binding IsChecked, Mode=TwoWay}"`：
WPF 只认 `PropertyChanged("IsChecked")` 通知 → 批量勾选时数据变了、
界面 CheckBox 完全不刷新。`IsChecked` 的 setter 里同样是 `Raise()`，
但那里的调用者恰好就是属性 setter，所以**手动点方框一直正常**，
只有「全选 / 清空 / 刷新恢复」这类批量设置出问题 —— 很容易误判成
「全选按钮没接线」。

### 修法

1. 两处批量设置改 `Raise(nameof(IsChecked))`；两处 setter 也显式写死，
   不再依赖 `[CallerMemberName]` 的巧合。
2. 表头三态提到公共层 `States.CheckAllState(k, n)`
   （`none` / `partial` / `all`），营列表与课程表共用一套词，
   `SyncAllCampsCheckbox()` / `UpdateLessonHeaderState()` 都走它。
3. `ChkAllCamps_Click` 的意图不再读缓存的 `_campHeaderState`，
   直接按真实勾选数 `CheckedCamps().Count < _campItems.Count` 决定
   全勾 / 全清；个别营方框变动由 `CheckChanged` 回调回写表头三态。
4. `SetCheckedSilently` 保持「**不发** `CheckChanged`」，
   否则全选 9 个营会触发 9 次课表重建（多营合并 = 9 次网关请求）。

### 验证

- `Xqd.Tests` 通过 `<Compile Include>` **直接链接编译 GUI 的 ViewModel 源码**
  （纯数据类、无 WPF 依赖），新增 K 组 25 项断言：通知名 / 静默批量 /
  CheckChanged 次数 / 三态映射 / 课程行同机制。合计 **224 项全绿**。
- 另建临时 WPF harness，用真实 `CheckBox` + `Binding("IsChecked", TwoWay)`
  实测：**12 项全绿**（全选 9 框齐勾、手动取消→partial、勾回→all、
  全不选 9 框齐清、课程行 3 框同样）。
- Release 编译 0 错 0 警；版本号 `States.AppVersion` 提到 `1.5.2`。
- ★ 交付时注意：用户当前实例可能正在下载（截图里 158 个排队），
  **不要结束进程、不要覆盖被锁的 DLL**，发布到独立目录，
  等用户关闭窗口后再整目录替换（历史与分片缓存保留，可续传）。

### 发布状态（2026-11-08 03:40）

  GitHub Release `v1.5.2-csharp-wpf` 发布，附件为
  `xingqudao-downloader-csharp-v1.5.2.zip`（246,081 字节）。
- 用户旧窗口关闭后，默认启动目录 `dist-csharp/gui/` 已整目录替换为 v1.5.2

## O. v1.5.3：干净 CI 构建才会暴露的两个坑（2026-11-08）

本机打包 / 编译一直正常，换到 GitHub Actions 的全新 runner 后第一次跑**两个作业同时失败**。
这两条与业务逻辑无关，但会让 CI 发版直接中断，属于「本机增量构建掩盖」的典型。

### 1. Windows runner 控制台是 cp1252，Python 打印中文直接崩

`build_exe.py` 里有 `print('收集 %d 个 Qt DLL + plugins/' % ...)`，
在 Actions 的 PowerShell + Python 3.13 环境里 stdout 编码是 **cp1252**：

```
UnicodeEncodeError: 'charmap' codec can't encode characters in position 0-1
```

本机控制台是 UTF-8，所以从未复现。修法：工作流顶层设
`PYTHONIOENCODING: utf-8` 与 `PYTHONUTF8: "1"`（子进程同样继承）。
**不要改业务代码去删中文输出** —— 问题在宿主编码，不在脚本。

### 2. XAML 引用**同程序集**自定义控件在干净构建时报 MC3074

```
The tag 'MarqueeControl' does not exist in XML namespace
'clr-namespace:Xqd.Gui.Controls'.      MainWindow.xaml(161)
The tag 'StateColorConverter' does not exist ... Theme.xaml(6)
```

类明明是 `public`、`namespace Xqd.Gui.Controls;`，本机 Release 编译 0 错 0 警 ——
是本机 `obj/` 里存量生成文件（`MainWindow.g.cs` 等）让增量构建跳过了
markup compile。干净 checkout 时 WPF 的 pass 1 解析不到**本地程序集**里的类型，
`Theme.xaml`（无 `x:Class` 的 `ResourceDictionary`）尤其容易触发。

⚠️ **试过但无效的修法**：给 `clr-namespace` 补
`;assembly=xingqudao-downloader`（本项目的 `AssemblyName`，不是 `Xqd.Gui`）。
第二轮 CI 仍报同样两条 MC3074 —— 指向本地程序集时仍要走本地类型解析，
加 `assembly=` 救不了。也**不是** SDK 版本问题：`global.json` 锁到
8.0.x 后 CI 用的是 8.0.427，与本机 8.0.416 同属 8.0.4xx，错误一致。

✅ **有效修法：把这两个控件挪出 GUI 程序集。**
新增 `src/Xqd.Controls`（`net8.0-windows` + `UseWPF` 类库）容纳
`MarqueeControl.cs` / `StateColorConverter.cs`（命名空间保持 `Xqd.Gui.Controls`），
`Xqd.Gui.csproj` 加 ProjectReference，两处 XAML 改为：

```xml
xmlns:ctrl="clr-namespace:Xqd.Gui.Controls;assembly=Xqd.Controls"
```

这样 MarkupCompile 从**已编译好的引用程序集**里取类型，是 WPF 的标准路径，
不再依赖临时程序集 / pass 2。`MainWindow.xaml.cs` 的
`using Xqd.Gui.Controls;` 不用改；`Xqd.sln` 随之变成 6 个项目。

另外加根目录 `global.json`（`8.0.100` + `rollForward: latestFeature`）
把 SDK 锁在 8.0.x，避免 runner 预装的更高版本 SDK 改变编译行为。

### 3. 离线回归还依赖本机时区和 ffmpeg 存在

`Xqd.Tests` 的 A 组用 `2025-03-12T12:00:00+08:00` 断言
`Naming.FmtWhen(ms) == "03.12 12:00"`；实现（与 Python 版 `fromtimestamp`
一致）用**本机时区**，runner 默认 UTC 会得到 `03.12 04:00`。
→ CI 里 `tzutil /s "China Standard Time"`，并设 `TZ=Asia/Shanghai` 兜底。

G 组只验证 `MediaProbe.FindTool` 的 PATH 查找逻辑（**不执行** ffmpeg），
但 runner 没装 ffmpeg，`FindTool` 会抛 `找不到 ffmpeg.exe`。
→ 在 `$RUNNER_TEMP/xqd-tools` 放两个占位 `ffmpeg.exe` / `ffprobe.exe`
并写入 `$GITHUB_PATH`，比联网装 ~100 MB 的 Chocolatey 包更快更稳。

### 4. 完整 `PySide6` 元包会把 exe 撑到 330 MB

`build_exe.py` 会把 `PySide6/` 顶层所有 `.dll` / `.json` 用 `--add-data`
收进单文件 exe。本机只装了 `PySide6_Essentials`（90 个文件、110.9 MiB），
产物 96.5 MiB；CI 上写 `pip install PySide6==6.12.0` 会连带装
`PySide6-Addons`（QtWebEngine / Qt3D / Charts 等 DLL），产物变成
**330,274,069 字节**，是原来的 3.3 倍 —— 在流量昂贵、网络不稳的场景完全不可接受。

→ 工作流改 `pip install "PySide6-Essentials==6.12.0"`，并在安装后断言
`PySide6/` 顶层 DLL 总量 `< 150 MiB`，防止以后有人改回完整元包。
README「依赖」栏本来就写的是 `PySide6-Essentials`，是工作流没对齐。

### 5. immutable release 不能用 `--clobber` 换附件

第一次发布成功后想用瘦身后产物覆盖附件，`gh release upload --clobber` 报：

```
HTTP 422: Cannot delete asset from an immutable release
```

GitHub 对已发布的 Release 默认开启不可变：附件、标题、正文都不能改，
但**整个 Release 可以删除**（tag 不动）。→ 工作流改为
`gh release delete <tag> --yes` 再 `gh release create`，同版本重跑即可换附件。
⭐ 因此**发版前要先在本地核对产物体积**，否则得删 Release 重建一次。

### 结论

发版链路变更后，**判断「能不能编译」必须以干净 checkout 为准**；
带 `obj/` / `dist/` 缓存的本机构建不能作为验收依据。
XAML 里用到的自定义类型，尽量放在被引用的独立程序集里。
