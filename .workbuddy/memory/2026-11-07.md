### 核心改动

| 文件 | 改动 |
|---|---|
| `xqd_engine.py` | 进度回调扩为 `(down, total, done_dur, total_dur)`；新增 `on_phase` 回调（解析/下载/封装/校验）；`_dl_all` 采样前 3 片**写盘复用** |
| `xqd_gui.py` | 新增 `SpeedMeter` / `fmt_dur` / `fmt_speed`；任务表 5→6 列；`_on_progress` 重写；新增 `_on_phase` / `_compute_eta` / `_job_eta` / `_refresh_task_row` / `_update_global_eta` / `_tick_eta` |

表头：`['', 课程, 状态, 大小, 速度, 剩余时间]`

### ★ 关键设计决策（别改回去）

1. **进度用「时长占比」不用「字节占比」**
   清单里每片时长是**精确已知**的；总字节数是拿前 3 片**外推的估算**，
   按字节算百分比会随片长差异产生误差。ETA 建立在时长上才准。

2. **速率用「最近 8 秒滑动窗口」不用「全程平均」**
   全程平均会让 ETA 在下载刚开始时严重偏大，且网络波动后反应迟钝。
   `SpeedMeter._calc_speed` 里：>6 秒没有新进度 → 速率归零（不报假速度），
   但 `last_speed` 保留，供兜底。

3. **ETA = 剩余量 ÷ 实时速率**（不是「已用时间 × 总时长/已用时间」）
   后者是平均速度推算，网络一慢就完全不跟手。

4. **暂停时冻结倒计时**（`_tick_eta` 里判 `control.is_paused()`），
   否则速率归零会让倒计时突然跳成 `--`，看着像任务丢了。

5. **完成任务后最后一列显示「用时 xx:xx」**
   → `job['finished'] = True`，`_refresh_task_row` 见到就 return，
   **否则定时刷新会把「用时」覆盖回估算值**（踩过）。

6. **封装阶段另算**：`eta_fixed = 总大小/10MBps + 时长/60 + 3s`；
   校验阶段固定 3s。

## ★★ 闪窗修复：Windows Terminal 闪窗（本轮）

用户反馈「工具启动时，有几次一闪而逝的窗口」。

### ★ 根因（用窗口枚举器实测定位，别猜）

Windows 11 的默认控制台宿主是 **Windows Terminal**。
打包的 exe 是 `--windowed`（**自身无控制台**），但它要启动的程序
**全是控制台子系统**：

| 程序 | 何时调 |
|---|---|
| `MuMuManager.exe` | 授权链路调 4~5 次（info / control launch / sh / app close） |
| `tasklist` | 判断 MuMu 主程序是否在跑 |
| `ffprobe` / `ffmpeg` | 探测成品时长、转封装 |

**Windows 的规则**：
- 控制台程序从「**已有控制台**」的父进程启动 → **继承**父进程控制台，
  **不会新建窗口**
- 从「**无控制台**」的父进程启动 → **新建**一个控制台，
  并拉起 **Windows Terminal** 来托管 → Terminal 窗口闪一下就消失

实测抓到的（修复前）：
```
3.54s  CASCADIA_HOSTING_WINDOW_CLASS  WindowsTerminal.exe  可见=True
       标题 = D:/Program Files\Netease\MuMu\nx_main\MuMuManager.exe
3.62s  PseudoConsoleWindow             MuMuManager.exe
5.25s  PseudoConsoleWindow             ffprobe.exe
5.36s  CASCADIA_HOSTING_WINDOW_CLASS  WindowsTerminal.exe  可见=True
       标题 = ...\ffmpeg-8.0.1-essentials_build\...
```

### 修复

新增 **`xqd_proc.py`**（项目根）—— 统一的「无控制台窗口」子进程调用层：

```python
si = subprocess.STARTUPINFO()
si.dwFlags |= subprocess.STARTF_USESHOWWINDOW
si.wShowWindow = 0                    # SW_HIDE
kwargs = {'creationflags': subprocess.CREATE_NO_WINDOW,   # 0x08000000
          'startupinfo': si}
```

`CREATE_NO_WINDOW` 让子进程**连控制台都不分配** → Terminal 完全不被拉起。
`STARTUPINFO/SW_HIDE` 是第二道保险。

替换点（GUI 链路的**全部**子进程调用）：
- `xqd_auth.py` 9 处 `subprocess.run` → `xqd_proc.run`
- `xqd_engine.py` 3 处 `check_output` + 1 处 `run` → `xqd_proc.*`
- `xqd_gui.py` 移除未用的 `subprocess` 导入
- `build_exe.py` `HIDDEN` 加 `'xqd_proc'`（否则打包后 import 失败）

### ★ 诊断工具（可复用）

`_lel/api/spy_windows.py` —— 枚举启动期间出现的所有新窗口
（类名 / 标题 / 进程名 / 是否可见）。定位闪窗神器：

```python
ctypes EnumWindows + GetClassNameW + IsWindowVisible + QueryFullProcessImageNameW
```

要识别的宿主类名：
`CASCADIA_HOSTING_WINDOW_CLASS`（Terminal）/ `ConsoleWindowClass` /
`PseudoConsoleWindow`（ConPTY）。

### ★ 测闪窗的关键陷阱

**父进程必须用 `pythonw.exe`（无控制台）**！
从 bash/cmd 里的 `python.exe` 启动子进程 → 继承已有控制台 →
**测不出来**（对照组会假阴性）。

靶子也要用**纯控制台程序**（`cmd.exe`），不要用 python
（`pythonw` 是 GUI 版，`sys.executable` 在 pythonw 下指向 pythonw.exe）。

正确组合实测：裸 subprocess → **4 个** Terminal 窗口；
`xqd_proc` → **0 个**。

## GUI v6.1（2026-11-07 本轮）：修「速度显示不准」+「状态卡在解析中」

用户截图反馈两个 bug，实测定位并修复。

### Bug 1：速度列量纲错（显示 `248B/s`，实际 7 MB/s）

- `job['unit']`：`'dur'`（分片视频）/ `'byte'`（直链音频，无分片时长）
- `_compute_eta` / `_job_eta` / `_tick_eta` / `_update_global_eta` 全部按 unit 分流

实测：修复前 `51B/s`（真实 7.0MB/s）→ 修复后 `6.7MB/s`。
